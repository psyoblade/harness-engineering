# 최종 리뷰 출력 템플릿

code-review-chair 가 최종 md 를 이 구조로 작성한다. 결과물은 Bitbucket PR 에 그대로 붙여 넣는다.

## 작성 규칙
- 섹션 제목은 아래 `###` 줄을 그대로 쓴다 (lint-md.sh 가 검사한다).
- 채울 근거가 없는 섹션은 "해당 없음" 한 줄. 작성자만 아는 항목(의도, 검증 결과, AI 사용 범위, 리뷰 기한)은 근거가 없으면 `(작성자 기입)` 으로 남긴다.
- 심각도는 🔴 Critical / 🟠 Major / 🟡 Minor.
- 위치는 `[파일명:라인번호]` 또는 `[파일명:시작-끝]`. 경로는 저장소 루트 기준.
- 각 지적에 수정 방향을 한 줄로 단다.
- 신뢰도 80 미만 지적은 넣지 않는다.
- 코드 펜스는 짧은 코드 조각에만 쓰고 백틱 4개 이상은 쓰지 않는다. xml, yml 은 코드 펜스 없이 4칸 들여쓰기로 쓴다.
- "도구를 찾을 수 없음" 같은 도구 부재 안내는 쓰지 않는다.

## 구조

```
## PR 코드 리뷰

> 리뷰 대상: <SUMMARY 값 그대로>

### 1. 목적
- 이번 변경이 필요한 이유 1줄

### 2. 의도
- 리뷰어에게 확인받고 싶은 내용 1줄

### 3. 변경 사항
- 전체 규모: 파일 N개, +A/-D 줄, 커밋 C개
- `경로` — [기능 추가|버그 수정|리팩토링|설정 변경|의존성 변경] 변경 목적 1줄

### 4. 검증 결과
- 검증 환경·방법과 결과 1줄, 미검증 항목 명시

### 5. AI 사용 범위
- 사용한 AI 도구와 수정 범위

### 6. 리뷰 기한
- YYYY.MM.DD 퇴근 전

### 7. 이번 변경으로 발생할 수 있는 치명적 오류
- 🔴 [파일명:라인번호] 내용 — 수정 방향

### 8. 기존에 존재하던 심각한 오류
- 🟠 [파일명:라인번호] 내용 — 수정 방향

### 9. 개선하면 좋은 항목 제안
- 🟡 [파일명:라인번호] 내용 — 수정 방향

### 10. 설계 원칙 점검
| 원칙 | 구분 | 판정 | 근거 |
| --- | --- | --- | --- |
| 1. 핵심 기능 1개, 관심사 3개 이하 | 필수 | ✅/⚠️/❌ | 1줄 |
| 2. 관심사별 커밋 분리, 커밋 메시지 | 선택 | ✅/⚠️/❌ | 1줄 |
| 3. 단위/통합 테스트로 동작 확인 | 필수 | ✅/⚠️/❌ | 1줄 |
| 4. 라이브 서비스 변경 시 HA·내결함성 | 필수 | ✅/⚠️/❌/해당 없음 | 1줄 |
| 5. 장황하거나 현학적인 코드 없음 | 선택 | ✅/⚠️/❌ | 1줄 |

### 11. 작성자 확인 질문
1. 리뷰어가 머지 전에 작성자에게 확인할 질문
2. ...
3. ...
```

마지막 줄 다음에 미검증 관점이 있으면 `> [미검증: 관점명] 사유` 를 덧붙인다.
